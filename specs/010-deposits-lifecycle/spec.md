## Clarifications

### Session 2026-05-27

- Q: How should the performance decomposition reconcile with total return? → A: Exact reconciliation with an explicit `unattributed` residual bucket shown whenever components do not fully reconcile.
- Q: How should a position NFT acquired by transfer-in (not minted by the wallet) be treated? → A: Include the position with an `openedByTransferIn` flag; opened value and capital entered are valued at the transfer-in event with degraded confidence.
- Q: What is the default list state on first visit? → A: Status = open active by default; all pools; full covered date range.
- Q: How should the cross-link to Strategies behave before the Strategies surface ships? → A: Always render a labeled, disabled placeholder when the pool has Mellow exposure; activate as a live link once the Strategies route is available.
- Q: How is the position label composed? → A: Auto-derived, deterministic, non-editable in v1: `<token0Symbol>/<token1Symbol>-<poolKind> #<shortTokenId>`, where `<poolKind>` is the concentrated pool tick spacing (e.g., `100`, `2000`) for CL pools or `stable`/`volatile` for basic pools (e.g., `WETH/USDC-100 #12345`, `WETH/USDC-volatile #12345`, `USDC/cbBTC-2000 #12345`).

### Session 2026-05-27 (follow-up: cross-feature lessons + layout)

- Q: Should CL deposits expose the position's price band and in/out-of-range state? → A: Yes. Detail surface MUST show `rangeLowerPrice` / `rangeUpperPrice` (token1-denominated, sourced from the existing analysis read model) and the current `isInRange` indicator, with explicit `tickLower` / `tickUpper` available for explainability. When range data is unavailable, render `—` and degrade confidence; never invert the price direction or fabricate a band.
- Q: Does the headline capital metric use gross lifetime flows or net contributed principal? → A: Headline KPIs and the list "opened value" use net contributed principal (`capitalEnteredUsd - capitalWithdrawnUsd`); gross `capital entered` and `capital withdrawn` remain visible inside the detail's Performance decomposition. Mirrors the Pools fix.
- Q: Where does the coverage / analysis-status banner live? → A: Reuse the existing global coverage surface; Deposits MUST NOT introduce a duplicate top-of-page coverage banner. Per-deposit coverage and confidence are shown inline at the row and detail level only.
- Q: How is filter and sort state preserved across navigation and Pools→Deposits cross-links? → A: Derived from URL query params (status, pool, dateRange, return sign, sort, page), not held only in component state. Avoids `react-hooks/set-state-in-effect` violations and supports deep links, back/forward, and pre-filtered arrival from Pools.
- Q: How should rewards in USD be rendered when `reward_events.amount_usd` is null for older claims? → A: Materialization MUST value such rows from `amount_raw + token_address + price_points` at read-model time and surface a USD figure; if no historical price exists for that day, the row carries an explicit "price unavailable" state and does not fall back to a future/latest price.

## Feature Selection Context

Specs 001–009 cover the design system, landing, connected overview (recent + protocol positions + asset trust), settings, analysis jobs, and pools list/detail. The historical analysis engine (`apps/web/src/server/analysis/enginePersistence.ts`) already persists `deposits`, `strategies`, `strategyExposures`, `ledgerEvents`, `assetMovements`, and `rewardEvents`. Per `docs/spec/the-cab-product-technical-spec.md` §14, the next phase (Phase 4) opens with **Deposits**, and §12.4 defines it as the manual-position lifecycle surface that turns the now-complete pool reconstruction into actionable position-level insight. This is the highest-value next step for an analyzed user: knowing not only *which* pools they touched (Pools), but *how each individual position they opened performed across its lifecycle*.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Review All Manual Deposits Across History (Priority: P1)

As an analyzed user, I need a Deposits view that lists every manual Aerodrome position I opened within the covered history window so I can quickly see what is still open, what closed, and how each performed relative to capital deployed.

**Why this priority**: The list is the entry to position-level analytics. Without it, the user can see pools they participated in but cannot identify the individual deposits inside those pools, when each opened and closed, or which carried the bulk of the result. It is the discovery layer for everything else in this feature.

**Independent Test**: Can be fully tested by opening Deposits after historical analysis is `ready` for a wallet with at least one decoded manual Aerodrome position, and verifying that every reconstructed deposit appears with identity, pool, status, opened/closed dates, opened/current value, rewards, realized and unrealized PnL, estimated annualized return, coverage and confidence — and that filters narrow the set without hiding coverage warnings.

**Acceptance Scenarios**:

1. **Given** a wallet with completed historical analysis and at least one decoded manual Aerodrome position, **When** the user opens Deposits, **Then** the list shows every position within the covered window with position label, pool identity, status (open/closed), open date, close date when applicable, opened value, current or closed value, total rewards, realized PnL, unrealized PnL, estimated annualized return, coverage state, and confidence.
2. **Given** the list is visible, **When** the user filters by open, closed, manual-only, by pool, by date range, by positive or negative return, **Then** the results update to match the selected criteria without hiding coverage warnings, and an empty filter result is presented as an explicit empty state rather than a generic blank view.
3. **Given** the wallet holds Mellow strategy exposure but no manual Aerodrome positions, **When** the user opens Deposits, **Then** the feature shows an explanatory empty state that distinguishes "no manual deposits" from "no on-chain activity" and points the user toward the Strategies surface for automated exposure.
4. **Given** historical analysis has never completed successfully for the wallet, **When** the user attempts to reach Deposits, **Then** the feature remains locked with the same gating treatment used by Pools, clearly explaining that position lifecycle analytics require analyzed history.

### User Story 2 - Inspect One Position Across Its Lifecycle (Priority: P1)

As an analyzed user, I need a rich position detail view that reconstructs the full lifecycle of a single manual Aerodrome deposit so I can understand exactly what I did, what happened to my capital, and how the result decomposes into rewards, asset price effect, and rebalance effect.

**Why this priority**: The product promise for Deposits is not just enumeration. It is being able to explain a position end to end: when it opened, every change after, every claim, the close (if any), and the breakdown of the result. Without this, Deposits is a glorified row list and does not earn the "control tower" framing.

**Independent Test**: Can be fully tested by opening a position with at least an open, an increase or stake, a claim, and either a close or a still-open state, and verifying the detail view shows the lifecycle timeline in chronological order, a value chart that tracks opened capital + additional capital + rewards versus current/closed value, a token movement table with USD value and price source per row, and a performance decomposition that ties back to the same numbers shown in the list.

**Acceptance Scenarios**:

1. **Given** a manual position with analyzed history, **When** the user opens its detail view, **Then** the feature shows a header with position label, pool, strategy link when relevant, status, open and close dates, the underlying token-id reference, current value, and total return.
2. **Given** the same position, **When** the user views the lifecycle timeline, **Then** the feature shows mint/deposit, stake, increase liquidity, claim, unstake, decrease liquidity, collect fees, withdraw, burn, and close events in chronological order, each with timestamp, transaction hash, event type, token movements, USD value, confidence, and a link to the block explorer.
3. **Given** the same position, **When** the user views the value chart and the performance decomposition, **Then** the feature exposes opened value, additional capital, rewards, current value, withdrawal events, closed value (when applicable), capital entered, capital withdrawn, fees and rewards claimed, realized PnL, unrealized PnL, asset price effect, rebalance effect when applicable, and estimated annualized return, all consistent with the list values for the same position.
4. **Given** a position with covered history shorter than the analysis window, **When** the user inspects the detail, **Then** the feature shows the actual covered range, makes the limit explicit, and does not invent values outside that range.

### User Story 3 - Keep Manual And Automated Exposure Cleanly Separated (Priority: P1)

As an analyzed user, I need Deposits to surface only manual Aerodrome positions and to cross-link to Strategies for any Mellow exposure attached to the same pools so I never confuse a position I directly own with automated strategy exposure I do not directly hold.

**Why this priority**: The product spec explicitly forbids modeling Mellow exposure as a manual deposit unless the wallet actually owns the underlying Aerodrome NFT. Mixing them would corrupt every downstream metric (realized PnL, rebalance attribution, annualized return) and break the canonical separation between `Deposit` and `StrategyExposure`. This rule must be testable at the feature surface, not buried in the engine.

**Independent Test**: Can be fully tested by using a wallet that holds both a manual Aerodrome NFT position and Mellow strategy exposure in the same pool, and verifying that Deposits lists only the manual position, that the detail page offers a non-modal cross-link to the relevant Strategy/StrategyExposure surface, and that no Mellow lifecycle event (deposit, stake, claim, unstake, withdraw, close) appears as a row inside the manual position's lifecycle timeline.

**Acceptance Scenarios**:

1. **Given** a wallet with both a manual Aerodrome NFT position and Mellow exposure in the same pool, **When** the user opens Deposits, **Then** only the manual position appears as a Deposit and the Mellow exposure is referenced via a clearly labeled cross-link rather than mixed into the list.
2. **Given** a manual position whose pool also has Mellow strategy exposure, **When** the user opens the position detail, **Then** the lifecycle timeline contains only manual `mint_position`, `increase_liquidity`, `stake`, `claim_reward`, `unstake`, `decrease_liquidity`, `collect_fees`, `withdraw`, `burn`, and `close` events; Mellow `mellow_*` events are not interleaved.
3. **Given** a Mellow deposit that returned tokens to the user wallet, **When** the analysis attributes those returned tokens to residual inventory, **Then** Deposits does not retroactively create a manual position for that flow and instead, when relevant, surfaces it through the cross-link or through residual context already owned by Pools.

### User Story 4 - Trust Partial Or Inferred Position Analytics (Priority: P2)

As an analyzed user, I need Deposits to stay honest when reconstruction is partial so that incomplete lifecycle data, missing prices, or ambiguous classifications never produce overstated PnL or fabricated precision.

**Why this priority**: Honest explainability is a core product promise. A position with missing price coverage or an ambiguous lifecycle event must remain visible with downgraded confidence rather than be hidden, deleted, or rounded into apparent certainty. This is the same trust contract Pools already enforces and Deposits must match it.

**Independent Test**: Can be fully tested by using a wallet with at least one position that has missing prices at one event, one ambiguous classification, and one event whose USD value cannot be fully resolved, and verifying that the list and detail show the position with explicit coverage and confidence indicators, that affected metrics degrade gracefully, and that the user is shown the reason rather than a silent gap.

**Acceptance Scenarios**:

1. **Given** a position with missing prices on one or more events, **When** the user views the list or detail, **Then** the position is shown with a coverage state and confidence indicator, affected metrics are presented as partial rather than as fabricated values, and the missing-price events are labeled with their price source state.
2. **Given** a position with an ambiguous classification (for example, a swap that the engine cannot confidently mark as a rebalance), **When** the user views the lifecycle timeline, **Then** the event remains visible, is labeled as ambiguous, and does not silently inflate or deflate realized PnL.
3. **Given** a position with covered history shorter than one year, **When** the user selects the longest available range, **Then** the value chart and decomposition show only the covered window and explicitly disclose the limit.

---

### User Story 5 - Filter, Sort, And Reach Detail Efficiently (Priority: P3)

As an analyzed user with many manual positions, I need useful filters, sort orders, and direct paths from Pools to Deposits so I can find the position I care about without scrolling through everything.

**Why this priority**: Quality-of-life. The feature is usable with P1/P2 alone, but at portfolio scale (dozens of positions) discovery becomes the bottleneck. Sort and pool-targeted entry from the existing Pools surface multiply the value of the underlying data without changing the data itself.

**Independent Test**: Can be fully tested with a wallet that has at least ten positions across multiple pools and statuses, verifying that filters compose (status + pool + return sign + date range), that at least one stable sort order is supported (e.g., open date descending), and that navigating from a Pool detail to the deposits in that pool pre-filters the Deposits list to that pool.

**Acceptance Scenarios**:

1. **Given** a wallet with positions across multiple pools and statuses, **When** the user combines filters (e.g., closed + pool X + negative return), **Then** the result set reflects every active filter and the active filters are visible and individually clearable.
2. **Given** the Pools detail page for a pool the user participated in manually, **When** the user follows the "see deposits in this pool" affordance, **Then** the Deposits list opens pre-filtered to that pool with the filter chip visible and clearable.
3. **Given** the user has sorted the list (e.g., by opened value descending), **When** they navigate to a position detail and return, **Then** the previously applied filter and sort state is preserved during the session.

### Edge Cases

- A position is opened, fully withdrawn, and the same NFT token id is later re-used or burned; the feature must not merge two economically distinct lifecycles into one row.
- A position is opened with capital coming partly from a prior pool withdrawal (rebalance source); decomposition must reflect rebalance effect rather than fresh capital.
- A position is partially decreased without closing; status must remain `open`, opened value must remain stable, and capital withdrawn must reflect the partial decrease.
- A position's pool has both manual and Mellow exposure with the same underlying tokens but different lifecycle shapes; cross-links must remain unambiguous about which surface owns which lifecycle.
- A position's last lifecycle event sits inside the covered window's edge while the close event sits outside it; the feature must label the position as "covered range ends before close" rather than showing a misleading still-open state.
- A position has fee collection events but no liquidity changes during a sub-range; the value chart must not interpolate misleading curves between sparse events.
- A wallet receives an Aerodrome NFT by transfer rather than by minting; the position is included with the `openedByTransferIn` flag, opened value and capital entered are taken from the transfer-in event with degraded confidence, and downstream PnL is computed from that baseline rather than invented.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Deposits feature MUST remain locked until the connected wallet has a successful historical analysis run on the active chain, mirroring the gating already in place for Pools.
- **FR-002**: The Deposits list MUST include every manual Aerodrome position decoded from analyzed history within the covered window, identified by Aerodrome NFT token id (or by an equivalent stable manual-position reference when an NFT id is not applicable) and never by a Mellow share reference.
- **FR-002a**: Positions whose first known lifecycle event is a transfer-in (the wallet received the NFT rather than minting it) MUST be included in the Deposits surface with an `openedByTransferIn` flag; opened value and capital entered MUST be valued at the transfer-in event timestamp using the standard price source, and the position's confidence MUST be degraded to reflect that the originating capital flow did not occur in this wallet.
- **FR-003**: The Deposits list row MUST expose, at minimum: position label, pool identity, current status (open/closed), open date, close date when applicable, opened value, current or closed value, total rewards, realized PnL, unrealized PnL, estimated annualized return, coverage state, and confidence indicator.
- **FR-003a**: The position label MUST be auto-derived deterministically from analyzed pool and position identity as `<token0Symbol>/<token1Symbol>-<poolKind> #<shortTokenId>`, where `<poolKind>` resolves to the concentrated-liquidity tick spacing for CL pools (e.g., `100`, `2000`) or to `stable`/`volatile` for basic pools, and `<shortTokenId>` is a stable, collision-safe shortened form of the NFT token id; the label MUST NOT be user-editable in v1 and MUST be identical across the list row, detail header, breadcrumbs, and cross-surface references for the same position.
- **FR-004**: The Deposits list MUST support filtering by: open, closed, manual (always-on for this surface), pool, date range, and positive vs negative return; and MUST visibly show active filters with individual clear affordances.
- **FR-005**: The Deposits list MUST support at least one stable, named sort order (default: open date descending) and MUST preserve the user's filter and sort selection during the session as they navigate to and from detail views.
- **FR-005a**: On first visit (no prior session selection), the list MUST default to: status filter = open, all pools, full covered date range, sort = open date descending; the "open" filter chip MUST be visible and clearable so the user can reveal closed positions in one interaction.
- **FR-006**: The Deposits list MUST present an explicit empty state when the wallet has no manual deposits, distinguishing "no manual deposits" from "no analyzed activity" and pointing the user toward Strategies when Mellow exposure is present.
- **FR-007**: The position detail header MUST show position label, pool, status, open and close dates, the token-id reference (or manual-position reference), current value, and total return, all reconciled with the same numbers shown for that position in the list.
- **FR-008**: The position detail MUST render a chronological lifecycle timeline covering, where present: mint/deposit, stake, increase liquidity, claim, unstake, decrease liquidity, collect fees, withdraw, burn, and close; each event row MUST show timestamp, transaction hash, event type, token movements, USD value, confidence, and a link to the block explorer for the active chain.
- **FR-009**: The position detail MUST render a value chart that distinguishes opened value, additional capital, rewards, current value, withdrawal events, and closed value (when applicable), and MUST NOT interpolate a continuous curve through ranges where no covered events exist.
- **FR-010**: The position detail MUST render a token movement table per lifecycle event with rows showing event, token, direction (in/out), amount, USD value at event, and price source.
- **FR-011**: The position detail MUST render a Performance panel that is split into two visually distinct surfaces so flow magnitudes are never mixed with return attribution: (a) a **Capital flow strip** — contextual, non-reconciling — showing gross `Capital entered` and gross `Capital withdrawn` (both valued at the USD prices observed at each contributing event, per FR-011b), and (b) a **Return attribution stack** — reconciling — exposing Rewards, Fees, Asset price effect, Rebalance / IL effect, Realized PnL, Unrealized PnL, and an explicit Unattributed residual (FR-011a). An `Est. annualized return` readout MUST render adjacent to the Total return row. All values MUST be numerically consistent with the list row for the same position.
- **FR-011a**: The Return attribution stack MUST exactly reconcile with Total return; when `Σ(Rewards + Fees + Asset price effect + Rebalance/IL effect + Realized PnL + Unrealized PnL) ≠ Total return` the gap MUST be surfaced as an explicit `unattributed` residual with a coverage/confidence reason, and MUST NOT be silently absorbed into any other component. `Capital entered` and `Capital withdrawn` are gross flow magnitudes and MUST NOT appear inside the reconciling sum.
- **FR-011b (LP / impermanent-loss accounting)**: Every `decrease_liquidity` (partial withdrawal), `withdraw`, `close`, and `burn` event MUST persist the USD value of the underlying token deltas using the prices observed at the event block. When a concentrated-liquidity position is **out of range** at the time of withdrawal and the position is therefore composed of a single token, the withdrawn token MUST be valued at its observed price at the withdrawal block; when no observation exists at that block, materialization MUST fall back to the nearest available `price_points` value within the configured tolerance window and add `priceFallbackDca` to `coverage_reason_codes`, never to a future/latest price beyond that window. The Rebalance / IL effect component MUST capture the LP-vs-HODL delta materialized at each `decrease_liquidity` / `close` event, computed against the entry-weighted reference basket using prices at the withdrawal block; any subsequent swap of withdrawn tokens MUST contribute exclusively to Realized PnL (swap proceeds minus the withdrawal-block cost basis of that token) and MUST NOT be re-attributed to the IL effect.
- **FR-012**: The feature MUST NOT create a manual deposit from any Mellow lifecycle event; Mellow exposure MUST be excluded from the Deposits list and detail and MUST be reachable from the relevant position context via a cross-link to the Strategies surface.
- **FR-012a**: When the position's pool has Mellow strategy exposure for the connected wallet, the detail surface MUST render the Strategies cross-link as a labeled, visually disabled placeholder until the Strategies route is available, with a tooltip or equivalent affordance explaining that strategy exposure exists in this pool and will be reachable from this control once Strategies ships; once the Strategies route exists, the same control MUST activate as a live link to the matching Strategy/StrategyExposure without further spec change.
- **FR-013**: Lifecycle events MUST come exclusively from the analyzed manual-position event set (`mint_position`, `increase_liquidity`, `stake`, `claim_reward`, `unstake`, `decrease_liquidity`, `collect_fees`, `withdraw`, `burn`, `close`); Mellow `mellow_*` events MUST NOT appear in the manual lifecycle timeline.
- **FR-014**: When data is partial (missing prices, ambiguous classification, unresolved attribution), the affected position MUST remain visible, MUST carry an explicit coverage state and confidence indicator at the list and detail level, and affected metrics MUST be shown as partial rather than as fabricated values.
- **FR-015**: When the position's covered history is shorter than the maximum one-year window, the detail MUST disclose the actual covered range and MUST NOT extrapolate metrics or chart values beyond it.
- **FR-016**: All on-chain identity (positions, events, transactions) MUST be scoped by chain id so that switching the connected chain swaps the deposit set deterministically, with no cross-chain bleed in queries or cached state.
- **FR-017**: The feature MUST consume data exclusively from the historical analysis read models (deposits, ledger events, asset movements, reward events, attribution states) and MUST NOT issue ad-hoc provider calls for recent wallet state from the Deposits surface; recent wallet state remains the responsibility of Overview.
- **FR-018**: From the Pools detail surface, when the user has manual deposits in a given pool, a navigation affordance MUST exist that opens Deposits pre-filtered to that pool; the active pool filter MUST be visible and clearable on arrival.
- **FR-019**: All user-facing copy and numeric formatting MUST be locale-aware (English default, Spanish secondary), and MUST NOT contain hardcoded strings in components; numbers, currency, percentages, and dates MUST use locale-aware formatting helpers already established for Pools and Overview.
- **FR-020**: The feature MUST refresh its read models when the user triggers a re-analysis from the existing analysis control surface; the Deposits list and any open detail view MUST reflect the new analyzed state without manual page reloads, while preserving the user's filter, sort, and selection where the underlying entity still exists after refresh.
- **FR-021 (CL range exposure)**: For concentrated-liquidity positions, the detail surface MUST render the position's price band using `rangeLowerPrice` and `rangeUpperPrice` (token1-denominated) sourced from the existing analysis read model, alongside `tickLower` / `tickUpper` for explainability and the current `isInRange` indicator. When range data is unavailable, the UI MUST render an explicit `—` and degrade the position's confidence; it MUST NOT invert price direction or fabricate a band.
- **FR-022 (Capital metric — net vs gross)**: Headline summary KPIs and the list `opened value` column MUST present capital as net contributed principal (`capitalEnteredUsd - capitalWithdrawnUsd`). Gross lifetime `capital entered` and `capital withdrawn` MUST remain visible only inside the detail's Performance decomposition and MUST NOT be used as the headline number.
- **FR-023 (Coverage banner placement)**: Deposits MUST consume the existing global coverage/analysis-status surface already established by Overview and Pools and MUST NOT introduce a second top-of-page coverage banner. Per-deposit coverage and confidence remain inline at the row and detail level (FR-014).
- **FR-024 (URL-derived data state)**: The data-defining state of the Deposits surface — status, pool, dateRange (`from` / `to`), returnSign, sort, page, pageSize, and selectedDepositId — MUST be derived from URL query parameters so deep links, back/forward navigation, and Pools→Deposits cross-links (FR-018) survive without prop-to-state synchronisation in effects. Recipients of a shared URL MUST see the same row set the sender sees.
- **FR-024a (Client-persisted view preferences)**: Presentation preferences that do not change the data set — column-visibility toggled set and Table/Compact density — MUST be persisted client-side via `localStorage`, keyed by `(chainId, walletAddress)` so preferences follow the user rather than the link and never leak across wallets or chains. These preferences MUST NOT be encoded in URL query parameters and MUST NOT be inherited by recipients of a shared link. On first visit, defaults are Table density and the default-visible column set defined in [contracts/deposits-ui.md](contracts/deposits-ui.md).
- **FR-025 (Rewards USD backfill at materialization)**: Per-position reward rendering MUST tolerate `reward_events.amount_usd = null` by valuing the row at materialization time from `amount_raw + token_address + price_points` for the claim day; when no historical price exists for that day, the row MUST carry an explicit "price unavailable" state and MUST NOT fall back to a future or latest price.

### Layout & Visual Design Requirements (Deposits surface only)

*Scope note: this section governs only the Deposits page content area. The application chrome (left sidebar navigation, top-level shell, data-status surfaces, wallet chip) is NOT changed by this feature.*

- **FR-L01 (Page structure)**: The Deposits page MUST render a single content area with: a feature header (title + descriptive subtitle + a right-aligned "How it works" affordance), a horizontal filter bar, a summary KPI strip, a list region, and a detail region that opens on row selection.
- **FR-L02 (Filter bar composition)**: The filter bar MUST expose, left-to-right: a Status chip (defaulting to the FR-005a default), a pool selector chip (defaulting to all pools), a date range picker chip (defaulting to the full covered range), and a "More filters" overflow control for the remaining filters defined in FR-004. Active filters MUST appear as removable chips with individual clear affordances.
- **FR-L03 (Summary KPI strip)**: Above the list, six summary cards MUST be rendered in this order: (1) Total deposits with `N of M total` denominator distinguishing in-filter vs covered total, (2) Total capital deployed (net per FR-022, with `% of manual capital`), (3) Current value (with `% of capital`), (4) Total rewards (with `% of capital`), (5) Realized PnL (signed amount + signed %), (6) Unrealized PnL (signed amount + signed %). Each card MAY render a sparkline backed by analyzed history; sparklines MUST NOT extrapolate beyond covered range.
- **FR-L04 (List region)**: The list region MUST render a count header (`N deposits`), a density toggle between Table (default) and Compact, and a column-settings affordance. The Table density MUST expose the following columns in this catalog order, fully covering FR-003: Deposit (label per FR-003a + truncated owning address), Pool, Status, Opened, Closed, Opened value (with token amount sub-line), Current value (with token amount sub-line), Total rewards (USD), Realized PnL (signed USD + signed %), Unrealized PnL (signed USD + signed %), Total return (signed USD + signed %), Est. APR (signed %), Coverage, Confidence, and a row chevron opening the detail region. The default-visible subset of these columns is defined in [contracts/deposits-ui.md](contracts/deposits-ui.md); non-default-visible columns MUST be reachable via the column-settings affordance. Column visibility and density are client-persisted view preferences governed by FR-024a (not URL state). Compact density collapses Realized PnL, Unrealized PnL, Total rewards, and Est. APR into a single `Performance` cell that opens the detail pane. Pagination MUST be rendered at the footer with `Showing X to Y of N`, page navigation controls, and a page-size selector (default 10 per page).
- **FR-L05 (Detail region — desktop)**: On viewports at or above the desktop breakpoint, the detail region MUST render as a right-aligned pane on the same route, opened by row selection (FR-024 selectedDepositId) and closeable without leaving the page. It MUST contain, top-to-bottom: (a) a detail header with the position label, status chip, the chain-scoped NFT token-id (or equivalent manual-position reference per FR-007), a primary `View in explorer` link, and a close control; (b) an identity row showing the token-pair icons, the pool-kind badge (Concentrated LP / Basic Stable / Basic Volatile), and the fee tier; (c) two KPI tiles (Current value, Total return signed + %); (d) a secondary stats row (Est. APR, Total rewards, Realized PnL, Unrealized PnL, Coverage, Confidence); (e) a covered-range disclosure line that states the actual covered start/end and explicitly marks shorter-than-window coverage per FR-015; (f) the value chart (FR-009) plotting opened value, additional capital, rewards, current value, withdrawal events, and closed value (when applicable) as discrete event markers connected only between observed events — no continuous interpolation across uncovered ranges; (g) the Lifecycle timeline (chronological rows with date, event type, signed token deltas) and a `View all events` expander that opens the per-event movement table (FR-010) showing event, token, direction (in/out), amount, USD value at event, and price source; (h) the Performance panel split into two surfaces: (h1) a contextual **Capital flow strip** showing gross `Capital entered` and gross `Capital withdrawn` (valued at observed event-block prices per FR-011b), explicitly labeled as non-reconciling flow magnitudes; and (h2) the reconciling **Return attribution stack** as horizontal stacked bars over Rewards, Fees, Asset price effect, Rebalance / IL effect, Realized PnL, Unrealized PnL plus an explicit Unattributed bar (FR-011a), with a `Total return` row that MUST reconcile exactly within `1e-9`. An `Est. annualized return` readout MUST appear adjacent to the Total return row. The visual treatment MUST follow the brand spec (futuristic data-dense surface: Cab Gold reserved for the Total return reconciliation row, Signal Teal for positive components, neutral/danger tokens for negative components and the Unattributed bar, monospaced numeric column for component USD values); (i) the Strategies cross-link (FR-012a) when applicable; (j) a bottom CTA row with a primary `View in explorer` action and a secondary `Share` action.
- **FR-L06 (Detail region — below desktop breakpoint)**: Below the desktop breakpoint, the detail region MUST collapse to a full-screen view reachable from the row, with the same content order specified in FR-L05.
- **FR-L07 (Brand and tokens)**: The Deposits surface MUST use design-system tokens only: Cab Gold for the primary CTA, Signal Teal for positive / signal indicators, Alert Red for negative values, the neutral chip token for CLOSED status, and the Signal Teal chip token for OPEN ACTIVE. ### Key Entities

- **Deposit (manual Aerodrome position)**: A user-owned manual Aerodrome position, identified by chain-scoped NFT token id (or equivalent stable manual reference). Attributes include pool reference, status, open/close timestamps, opened value, current/closed value, capital entered, capital withdrawn, rewards claimed, realized PnL, unrealized PnL, asset price effect, rebalance effect, estimated annualized return, coverage state, and confidence.
- **Lifecycle Event**: A chronologically ordered ledger event tied to a single deposit. Attributes include timestamp, transaction hash, event type from the manual-position event set, token movements with direction and amount, USD value at event, price source, classification confidence, and coverage flags.
- **Asset Movement**: A token-level movement attached to a lifecycle event, used to populate the per-event token movement table. Attributes include token reference, direction (in/out), amount, USD value at event, and price source.
- **Reward Allocation (for a Deposit)**: The portion of reward events that the analysis engine attributes to a given manual position, used in the rewards column, value chart "rewards" stream, and the "fees and rewards claimed" component of the performance decomposition.
- **Coverage State (per Deposit)**: An explicit indicator combining covered-range bounds, price coverage, classification confidence, and attribution certainty; surfaces both in the list row and on the detail view.
- **Cross-link to Strategy Exposure**: A non-data-coupling reference that lets a Deposit's detail surface point the user to the relevant Strategy / StrategyExposure when the deposit shares a pool with Mellow exposure. It carries no Mellow lifecycle data into the Deposit itself.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An analyzed user with up to fifty manual positions can locate any specific position in the Deposits list within ten seconds using the supported filters and sort, without leaving the Deposits surface.
- **SC-002**: The performance decomposition reconciles exactly with total return for every position; any gap between the sum of attributed components and total return is rendered as an explicit `unattributed` residual bucket with a coverage/confidence reason, and zero positions silently absorb the gap into rewards, asset price effect, or rebalance effect
- **SC-003**: For positions with full coverage and high confidence, the performance decomposition explains the total return as the sum of its components (rewards + asset price effect + rebalance effect + residual) with a documented reconciliation rule; for partial-coverage positions, the reconciliation gap is shown explicitly rather than hidden.
- **SC-004**: For wallets that hold both manual Aerodrome positions and Mellow strategy exposure in the same pool, zero Mellow lifecycle events appear in the manual lifecycle timeline, and the cross-link to Strategies is reachable from the position detail in at most one interaction.
- **SC-005**: When the wallet's analysis transitions from `ready` to a successful re-analysis, the Deposits list reflects the new analyzed state within one user-perceived refresh cycle of the existing analysis control surface, without requiring a manual page reload.
- **SC-006**: Coverage-degraded positions remain visible in 100% of cases; no position is dropped from the list solely because of partial prices or ambiguous classification.
- **SC-007**: All user-facing copy renders correctly in both English and Spanish with no hardcoded strings detected by the established i18n lint checks, and all numeric/date renderings respect the active locale.

## Assumptions

- The existing Phase 2/3 analysis engine continues to populate `deposits`, `ledgerEvents`, `assetMovements`, `rewardEvents`, and `attributionStates` with the schemas already deployed; this feature does not introduce new persistence tables but may add read-only views or read-model helpers.
- The "covered history window" for a Deposit is bounded by the same wallet-level analysis window used by Pools (up to one year on Base for product v1).
- The active chain remains Base mainnet for product v1; chain awareness is implemented as scoping discipline, not as cross-chain feature delivery.
- When Strategies is not yet available, the cross-link is rendered as a labeled disabled placeholder (see FR-012a); when Strategies ships, the same control activates as a live link without further spec change.
- Mellow strategy exposure has, or will have, its own canonical surface (Strategies, §12.5) as a separate spec. Deposits ships with a non-coupling cross-link contract that gracefully degrades to "Strategies not yet available" until that surface exists, and is upgraded to a live link once it does.
- "Recent wallet state" remains the responsibility of Overview; Deposits never bypasses the analysis read model to fetch live wallet balances.
- The Pools surface (spec 009) is the canonical pool-level analytics; Deposits links into it for pool identity and does not re-implement pool-level metrics.
- Locale handling, formatting helpers, gating UI for "analysis required", and the analysis control surface established in specs 003/005/007/008/009 are reused and not re-specified here.
- The maximum number of manual positions a single wallet is expected to surface in v1 is bounded by the configured maximum wallet history size (§2.6 of the product spec); Deposits is sized for that envelope, not for unbounded wallets.
